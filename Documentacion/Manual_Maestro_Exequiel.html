01. Integración al Proyecto Local

Flujo inicial de sincronización de código y puesta en marcha del entorno para Exequiel.

¡Bienvenido al equipo de desarrollo, Exequiel! Esta guía técnica detalla los pasos de ingeniería de software para clonar el repositorio, sincronizar dependencias y poner en marcha la solución completa de forma local.

Sincronización del Código de Integración (Git)

Para evitar pisar código y mantener una disciplina ordenada de equipo, es imperativo actualizar tu copia local y trabajar sobre la rama de integración dev ejecutando los siguientes comandos en tu consola:

# 1. Obtener ramas remotas y cambios actualizados
git fetch origin

# 2. Posicionarse en dev y sincronizar con rebase
git checkout dev
git pull --rebase origin dev

Configuración y Levantamiento del Entorno Local

Prerrequisitos: .NET 8 SDK, Node.js 18 o 20 LTS, SQL Server Express / LocalDB y ABP CLI. El levantamiento secuencial se estructura en tres pasos:

1

Restaurar Base de Datos y Semillas (DbMigrator)

Ejecutar el proyecto migrador en aspnet-core/src/TourismTracking.DbMigrator/ con dotnet run. Creará la base de datos física local en SQL Server, ejecutará las migraciones de EF Core y persistirá los datos iniciales.

2

Levantar Backend (.NET 8 Web API)

Ejecutar dotnet run en TourismTracking.HttpApi.Host/ para iniciar el servidor Web API (puerto 44305 y documentación Swagger interactiva).

3

Levantar Frontend (Angular 18)

Ingresar al directorio angular/, ejecutar npm install y arrancar la interfaz web con npm start (puerto 4200).

02. Arquitectura de la Solución y Convenciones de Código

Estructura en capas Domain-Driven Design (DDD), patrones de diseño y estándares técnicos.

La solución se fundamenta en los principios de Domain-Driven Design (DDD) provistos por ABP Framework, desacoplando la lógica de negocio de la infraestructura y asegurando alta mantenibilidad:

Estructura de Capas del Backend (.NET 8)
  • TourismTracking.Domain: Entidades raíz (Destination, Experience), entidades secundarias (Review, Notification), reglas de negocio y sembrado vía IDataSeedContributor.
  • TourismTracking.Application.Contracts: Interfaces públicas (IDestinationAppService), DTOs tipados y definiciones de permisos.
  • TourismTracking.Application: Implementación de servicios de aplicación, validación de reglas de uso y mapeos objeto-a-objeto con AutoMapper.
  • TourismTracking.EntityFrameworkCore: Contexto de base de datos (DbContext), mapeo relacional en Fluent API y migraciones.
  • TourismTracking.HttpApi.Host: Controladores REST, autenticación OpenIddict y endpoints expuestos a Angular.

Convenciones de Código y Buenas Prácticas

Para asegurar coherencia técnica en el trabajo en equipo, se establecen las siguientes directrices:

Estándares de Codificación y Configuración:
  • C# (.NET): PascalCase para clases y métodos públicos; camelCase con guion bajo (_repository) para dependencias inyectadas; operaciones I/O estrictamente asíncronas (async/await).
  • TypeScript / Angular: Nomenclatura kebab-case para archivos (list-destinations.component.ts); consumo estricto de proxies generados sin llamadas HTTP artesanales; suscripciones reactivas con RxJS.
  • Configuración: Centralizar cadenas de conexión en appsettings.json y URLs de entorno en environment.ts. Prohibido hardcodear parámetros en código.

03. Protocolo de Colaboración Git y Flujo de Trabajo en Equipo

Reglas de sincronización, validación pre-push y promoción formal hacia producción.

La colaboración simultánea entre Thiago y Exequiel sobre la rama dev requiere una disciplina rigurosa. Este protocolo garantiza que el código compartido siempre compile y mantenga estabilidad en las pruebas.

Sincronizar (Rebase)
Validar Local
Commit Semántico
Push Seguro
Compilación y Tests Obligatorios

Antes de realizar push a dev, cada desarrollador debe compilar localmente (dotnet build) y ejecutar la suite completa de pruebas unitarias (dotnet test). Si algún test falla, el push queda detenido.

Resolución de Conflictos

Al rebasar sobre dev, si surgen conflictos se analizan conjuntamente para preservar la lógica de negocio prevista, validando la compilación antes de continuar con git rebase --continue.

Secuencia de Integración Local Obligatoria

Todo integrante del equipo debe ejecutar este flujo secuencial exacto para subir cambios sin desestabilizar la rama compartida:

# 1. Sincronizar local con cambios remotos en dev
git pull --rebase origin dev

# 2. Validar integridad de compilación
dotnet build aspnet-core/TourismTracking.sln

# 3. Validar estabilidad de lógica de negocio (55 tests unitarios)
dotnet test aspnet-core/TourismTracking.sln

# 4. Crear commit semántico y subir
git add .
git commit -m "feat(destination): persistir destinos con filtros reactivos"
git push origin dev
Protección del Código de Entrega (Rama 'prod')

La rama prod está protegida en GitHub. Todo cambio debe promoverse mediante Pull Request (PR) formal revisado entre pares desde dev, adjuntando evidencia de pruebas y el Changelog Académico para la evaluación del Prof. Enzo Tanga.

04. Spec-Driven Development (SDD)

Uso de contratos en backend como única fuente de verdad (Single Source of Truth).

El Desarrollo Guiado por Especificaciones (SDD) garantiza la consistencia total entre Backend y Frontend. Al definir los contratos primero en C#, Angular se acopla dinámicamente mediante proxies, eliminando la escritura manual de llamadas HTTP y DTOs.

Contrato C# (.Contracts)
Compilar Backend
Generar Proxies (ABP CLI)
Pasos para la Creación de Endpoints y UI en Angular
  1. Crear Contrato en Backend: Escribir los DTOs y la interfaz del servicio (ej. IDestinationAppService) en el proyecto TourismTracking.Application.Contracts.
  2. Compilar la Solución: Ejecutar dotnet build en C# para actualizar la metadata del framework.
  3. Autogenerar los Proxies en Angular: Abrir la consola en la carpeta angular/ y ejecutar: 
    abp generate-proxy -t ng
  4. Consumir el Servicio: Angular tendrá automáticamente inyectable el nuevo servicio con todos sus DTOs tipados en TypeScript, listos para integrarse en tus componentes UI.
Justificación Académica ante la Cátedra

Utilizamos Spec-Driven Development bajo la CLI de ABP para garantizar que no existan inconsistencias de tipado o errores ortográficos en la comunicación API. Esto permite un acoplamiento limpio y desacoplado, permitiendo que el Frontend y el Backend avancen en paralelo basándose exclusivamente en el contrato DTO.
